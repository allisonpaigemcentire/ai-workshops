Foundation

One repository, multiple working trees

A linked worktree is another checkout of the same repository. It lets you work on separate branches at the same time without switching or stashing.

Separate per worktree

  • Working files and generated output
  • Staged changes and index
  • Checked-out branch and HEAD

Shared across worktrees

  • Commits and Git objects
  • Branches, tags, and remotes
  • Most repository configuration

Three rules

  • One branch per worktree. Git blocks the same branch in two worktrees; use another branch or a detached HEAD.
  • List before creating. Run git worktree list.
  • Remove with Git. Use git worktree remove; run git worktree prune for stale metadata.

Not a full playground

Worktrees separate files, not processes. Two apps can still compete for the same port, database, simulator, or device.

Hands-on lab

Common mistakes and recovery

❌ Delete directory manually

rm -rf ../repo-wt-feature

Git metadata left behind, worktree list shows it as prunable.

✓ Use git to remove

git worktree remove ../repo-wt-feature git worktree prune

Clean removal. Git cleans up both files and metadata.

❌ Same branch in two worktrees

git worktree add ../wt2 feature/auth # Already checked out in ../wt1

Git refuses. One branch per worktree only.

✓ Use a different branch

git worktree add -b feature/auth-v2 ../wt2 origin/main

Or use --detach for temporary checkouts.

Apply · AI coding agents

Both tools use the same Git primitive

Claude Code

One terminal per taskclaude --worktree feature-auth claude --worktree "#42"
  • Creates .claude/worktrees/<name>/ and branch worktree-<name>.
  • baseRef in .claude/settings.json: "fresh" starts from the remote default branch, "head" from your current commits. Committed state only.
  • Use .worktreeinclude to copy chosen gitignored files such as .env.

Cursor

  • /worktree <task> runs the rest of the chat in a worktree.
  • /best-of-n model1,model2 <task> runs parallel candidates; it compares, it does not merge.
  • /apply-worktree brings changes into the main checkout; /delete-worktree removes it.
  • Automate setup in .cursor/worktrees.json; watch the machine-wide cap, default 25.
Inside a Claude Code worktree session, edits and commands that target the main checkout are blocked, including for subagents. Do not assume every agent tool enforces the same boundary.
Apply · Workflow patterns

Parallel or sequential: tips for both

Parallel: different tasks

When: Two independent features or one writes code while another fixes bugs.

Example: Claude Code builds a new API endpoint in one worktree while Cursor refactors the database schema in another. Both commit their work; changes merge cleanly.

Setup: Each tool gets its own worktree on a different branch. Use `git worktree list` to verify before creating.

Sequential: same task

When: One IDE implements, the other reviews or refines. Handoff model.

Example: Claude Code writes a feature and pushes to a PR branch. Cursor checks out that branch in a new worktree, runs tests, writes a PR review, and applies improvements. Single branch, sequential edits.

Setup: First tool commits and pushes. Second tool pulls and creates a worktree on the same branch. Use `/apply-worktree` to merge changes back.

Key rule: One branch per worktree. If both IDEs work on the same branch, use the same worktree (sequential only). If they work in parallel, use different branches or different checkouts.
Apply · Advanced pattern

Fleet view: many agents, many PRs

Launch multiple agents in parallel, each in its own worktree and branch. Each commits and opens a PR. Track all PRs by branch and CI status.

Claude Code (IDE)

In the chat, spawn multiple agents in one message with `isolation: "worktree"` on each, or use Workflow tool with `agent(prompt, {isolation: 'worktree'})` inside `parallel()`.

Agent(prompt, {isolation: "worktree"}) Agent(prompt, {isolation: "worktree"}) Agent(prompt, {isolation: "worktree"})

Each agent runs in parallel, creates its own worktree under `.claude/worktrees/`, commits, and pushes a PR. Track with `gh pr list`.

Claude CLI

Spawn multiple `claude` processes in the background, each creating a worktree with `--worktree` flag and running independent tasks.

claude --worktree task-1 "task prompt 1" & claude --worktree task-2 "task prompt 2" & claude --worktree task-3 "task prompt 3" & wait

Each process runs in parallel. Instruct each to commit and push. Track with `gh pr list`.

Cursor

Sequential in one chat: use `/worktree task-1`, do work, `/apply-worktree`, then `/worktree task-2`, do work, `/apply-worktree`. One chat session, worktrees switch sequentially.

/worktree task-1 (do work, commit) /apply-worktree /worktree task-2 (do work, commit) /apply-worktree

Track with `gh pr list` or git log.

Apply

Try fleet view in your preferred tool

Claude Code (IDE)
  1. Open the playground repo in Claude Code.
  2. In one message, spawn 2–3 agents with `isolation: "worktree"` on each.
  3. Give each agent a simple, independent task (e.g., add comments to different files).
  4. Instruct each to commit and push to a branch named after the task.

Track: Run gh pr list to see the PRs. Agents run in parallel.

Claude CLI
  1. Open a terminal in the playground repo.
  2. Spawn 2–3 `claude` processes in parallel, each with `--worktree` and a task.
  3. Each process creates its own worktree, does independent work, commits, and pushes.
claude --worktree task-1 "prompt for task 1" & claude --worktree task-2 "prompt for task 2" & wait

Track: Run gh pr list. Processes run in parallel.

Cursor
  1. Open the playground repo in Cursor.
  2. Use /worktree task-1, make a change, /apply-worktree.
  3. Repeat with /worktree task-2, make a change, /apply-worktree.

One chat session. Worktrees switch sequentially, not in parallel.

Track: Run gh pr list or check git log.

Key difference: Claude Code and Claude CLI run agents in parallel (multiple at once). Cursor runs sequentially in one chat. All three produce separate branches and PRs.
